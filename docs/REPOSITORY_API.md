# Repository API contract

`Database` / `Queryable` from `src/db/database.ts`: `query<T>(sql, values?): Promise<{rows:T[]; rowCount:number}>`; Database adds `transaction(fn)` and `close()`. `PgDatabase(connectionString)` is production adapter. `migrate(db)` from `src/db/migrate.ts` applies checked-in SQL. PGlite can implement Database in tests/offline runtime; pass parameters arrays and normalize rowCount.

`new Repository(db)` exposes `readonly db` for scoped extension queries. All dates in service arguments/results are ISO strings. IDs are UUID strings generated by repository. Settings stored as JSON. Methods below are async:

- `ensureUser(telegramId:string): Promise<string>`
- `getSettings(userId): Promise<Settings|null>`; `saveSettings(userId, settings): Promise<void>`
- `addIdeas(userId, ideas: Omit<Idea,'id'|'userId'|'used'|'createdAt'>[]): Promise<Idea[]>`; `listIdeas(userId, unusedOnly=true): Promise<Idea[]>`; `claimIdea(userId, ideaId): Promise<boolean>`
- `createPost(userId, scheduledAt, ideaId: string|null, slotKey: string): Promise<Post>` (unique slot, idempotent); `getPost(userId,postId): Promise<Post|null>`; `listPosts(userId,limit=100): Promise<Post[]>`
- `getVersion(userId,postId,version): Promise<Version|null>`; `latestVersion(userId,postId): Promise<Version|null>`; `history(userId,limit=100): Promise<Version[]>` (latest versions incl published, suitable repetition history)
- `saveDraft(userId,postId,expectedVersion,content,instruction:string|null=null): Promise<Version>` (CAS; initial draft/postponed allowed; subsequent only waiting_approval/revision_requested/draft; invalidate approval)
- `approve(userId,postId,version,telegramUpdateId:string): Promise<Post>` (latest WAITING_APPROVAL, durable approval + publish job atomically, duplicates safe)
- `cancel(userId,postId,expectedVersion): Promise<Post>`
- `postpone(userId,postId,expectedVersion,scheduledAt): Promise<Post>` (invalidates approval, new resume job scheduled; old jobs fenced by state/version)
- `resumePost(userId,postId,scheduledAt?): Promise<Post|null>` (when due postponed → waiting_approval)
- `beginPublish(userId,postId,version): Promise<{post:Post;version:Version;attemptId:string}|null>` (only current approved version and explicit approval ledger; increments attempt; returns null on stale/redundant work)
- `completePublish(userId,postId,attemptId,result:PublishResult): Promise<void>`
- `failPublish(userId,postId,attemptId,reason,uncertain:boolean,retryAt?:string): Promise<void>` (uncertain permanently blocks auto retry; safe definite failures may atomically enqueue retry with existing approval)
- `recoverStalePublishing(beforeIso): Promise<number>` (publishing → publish_uncertain; never auto republish)
- `enqueueJob(userId,type,payload:Record<string,unknown>,runAt:string,dedupeKey:string): Promise<void>`
- `claimJobs(workerId,limit=10,leaseSeconds=120,userId?:string): Promise<Job[]>`; `completeJob(id,leaseToken): Promise<boolean>`; `failJob(id,leaseToken,error,retryAt?:string): Promise<boolean>`
- `enqueueOutbox(userId,text,buttons?:TelegramButton[][],postId?:string,version?:number,dedupeKey?:string): Promise<void>`
- `claimOutbox(workerId,limit=10,leaseSeconds=120,userId?:string): Promise<OutboxMessage[]>`; `completeOutbox(id,leaseToken,messageId): Promise<boolean>` (also records reply mapping + active session only when current version); `failOutbox(id,leaseToken,error,retryAt): Promise<boolean>`
- `acceptTelegramUpdate(userId,updateId:string,payload:Record<string,unknown>): Promise<boolean>` (dedup + telegram job atomically; job payload contains {updateId,update,target,targetCaptured:true}; target is the receipt-time message/session mapping or null, never bind a null target later)
- `recordInteraction(userId,postId:string|null,instruction): Promise<void>`; `conversation(userId,postId,limit=12): Promise<string[]>`
- `resolveMessage(userId,messageId): Promise<{postId:string;version:number}|null>`; `activeDraft(userId): Promise<{postId:string;version:number}|null>`

`Job` fields: id,userId,type,payload,attempts,leaseToken. `OutboxMessage`: id,userId,text,buttons,postId,version,attempts,leaseToken. `ConflictError` denotes invalid/stale user action. Published rows can be read using `db` with tenant filter. Tables use snake_case; JSON fields settings/content/payload/buttons. `post_versions.text` is composed via block texts joined by '\n\n'. Raw schema authoritative in migration.

Queue claims serialize one running business job per tenant using a user row lock; telegram jobs additionally maintain receipt order via queue_order even during retry backoff. The optional userId must be passed by a tenant-specific worker. Queue acknowledgement requires an unexpired matching lease token. Outbox independently retries delivery; Telegram has no sendMessage idempotency, so ambiguous delivery may produce duplicate notification messages but cannot create duplicate publishes.

`retryPublish(userId,postId,version)` permits manual retry only after a definite failure with matching approval. Automatic provider retries are capped at three total publish attempts; timeout/unknown outcomes never retry. Failure notifications include post/version message context so retry buttons can be verified. Re-approval after postponement records a fresh immutable approval and a fresh publish job even if the content version is unchanged.

Migration 002 adds tenant queue indexes and a database lifecycle trigger. publish_uncertain → published is reserved for explicit administrative reconciliation of a LinkedIn post already published. It does not invoke LinkedIn.
